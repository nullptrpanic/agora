# Sandbox Filesystem And Executable Preparation

`agora-sandbox` provides a rootless, process-tree-scoped filesystem view on macOS. Supported path operations read through to the host filesystem, while sandbox mutations use a persistent copy-on-write tree. The original host paths are never modified except for effective native-passthrough roots. `/dev` is always present so device operations retain kernel semantics; callers may explicitly add host directory roots through `filesystem.bypass` or `SandboxConfig::with_native_passthrough_root`.

The filesystem and network views are cooperative boundaries, not a kernel namespace, and apply only to processes that load the Agora hook library. Executable preparation fails closed when a process cannot be made injectable. The runner does not install a native macOS process sandbox or virtualize Keychain APIs; descendants use the current user's host Keychain directly.

## Storage Layout

`SandboxConfig::new` defaults the work directory to `~/.agora-sandbox`. The CLI reads optional `workdir` from the `run` configuration and uses the same default when it is omitted; the SDK exposes `SandboxConfig::with_workdir`.

`<workdir>/fs` is the only persistent filesystem backing tree. Absolute logical paths are mirrored below it: `/usr/bin/curl` maps to `<workdir>/fs/usr/bin/curl`. There is no disk image, mount point, or separate `filesystem` directory.

Control data is stored in place:

```text
<workdir>/fs/
├── .fs.lock
├── .key.json              # encrypted mode only
├── .metadata              # managed-directory root marker
├── .vfs.lock
├── .rekey.json            # only while key migration is recoverable
├── usr/
│   └── bin/
│       └── .metadata
└── ...
```

Every physical upper directory, including merge-only directories, contains one valid `.metadata` marker. The marker chain from `<workdir>/fs/.metadata` to an upper object is continuous; an empty version-3 marker is valid and does not make the directory authoritative over lower. Hidden `.agora-write-lease-*` sidecars track writable encrypted entries and protect in-flight plain-file publication. A direct path below `<workdir>/fs` or its canonical root is decoded as an alias of the corresponding logical absolute path and re-enters the normal VFS; malformed encoded components and decoded paths that target another private workdir location are rejected. The alias never returns backing storage directly, so raw metadata, locks, ciphertext, write leases, and executable-cache controls remain inaccessible and directory enumeration continues to hide them. Paths below `<workdir>/runtime`, `<workdir>/ca`, and other private workdir locations, including external symlink aliases, remain denied. A sandbox may still create a logical business file with a reserved control name such as `.metadata`, `.fs.lock`, `.key.json`, `.vfs.lock`, or `.rekey.json`; exact names, dot-suffixed variants, and internal backing-name prefixes use an encoded physical filename and remain separate from control data.

Controller-managed directory entries are opened without following their final symbolic link, verified as directories owned by the effective user, and secured before use. Managed regular control files—including `.fs.lock`, `.vfs.lock`, `.metadata`, `.key.json`, `.rekey.json`, write leases, the session startup lock, and default CA material—are opened with `O_NOFOLLOW`, then verified from the descriptor as same-user regular files; persistent controls are mode `0600`. A symbolic-link, non-regular, or foreign-owned substitution is rejected before the controller truncates, appends to, locks, or changes permissions on its target. This validation is lazy for per-directory metadata and write leases and does not add a recursive startup scan.

Automatically managed TLS CA certificate and key files remain under `<workdir>/ca`. Per-run client trust bundles and Java trust stores live in the owner-only temporary runtime directory and are removed with that runtime. The CLI materializes its embedded, linker-signed hook before sandbox startup at `<workdir>/runtime/hook/<md5>/libagora_sandbox.dylib`, using `<workdir>/runtime/hook/.lock` to serialize publication. The lowercase MD5 covers the complete dylib and matching regular-file content is reused without rewriting it. A same-user regular file with the wrong size, unreadable content, or a mismatched checksum is atomically replaced from the embedded bytes; foreign-owned files remain an error. This controller-owned runtime cache is outside `<workdir>/fs`: it has no overlay metadata, filename or content encryption, lower-layer fallback, or filesystem audit representation. Prepared SIP-restricted executables and required application-bundle startup images are persistent plaintext cache entries at their mirrored paths below `<workdir>/fs`; for example, `/usr/bin/curl` is cached at `<workdir>/fs/usr/bin/curl`. They are controller-managed executable or loader artifacts rather than encrypted business COW files and are reused only while their recorded source and destination identities, materializer, and target platform/architecture variant where applicable remain valid. Executable output retains an MD5 fallback; loader images are copied byte-for-byte and carry the same destination-validation fallback. Loader trees cache their full-body checksum in a bounded process-local cache after validating the complete entry set, per-entry device/inode/size/mtime/ctime/mode, and symlink targets. Unchanged trees are stat-scanned without rereading file bodies; changes trigger full checksumming, and preparation revalidates the source before publication.

## Storage Modes

The CLI treats its JSON configuration path as caller-managed input and does not enforce file ownership or permission bits. `filesystem.local.encrypt: "plain"` in that configuration selects the persistent `<workdir>/fs` tree without file-content encryption and rejects `filesystem.local.key`. Plain mode is the CLI and SDK default when the setting is omitted.

`filesystem.local.encrypt: "encrypted"` with a non-empty `filesystem.local.key`, or `SandboxConfig::with_encrypted_workspace`, selects encrypted mode. The non-empty check is structural, not a strength guarantee: operators must provide a high-entropy secret because a short or human-memorable value permits offline guessing by anyone who obtains the ciphertext tree. The first run creates `<workdir>/fs/.key.json` with a random salt and derived key identifier. Later runs derive the cipher again and reject a different key before starting the child. Existing unmanaged data is not imported into encrypted mode.

Encrypted regular files use content format version 2. Each container has two authenticated generation headers carrying a random file ID and logical length, followed by independently authenticated 4096-byte AES-256-GCM blocks. A per-file key is derived from the runtime cipher key and file ID with HKDF; each written block receives a fresh nonce and authenticates its file ID and block index. Absent or all-zero physical block slots represent sparse logical zeroes, so allocated block contents are authenticated but the sparse allocation map itself is not: removing or zeroing an entire slot can turn that block into a sparse zero. Content format version 1 is not supported, and encrypted deployments must start with a fresh `<workdir>/fs`.

Opening an encrypted container authenticates and selects its current header without changing its physical length. Ciphertext beyond that header's logical extent may belong to a live writer that has not published its next length yet; readers must not trim it. Explicit length changes own physical truncation. Path-based `truncate` uses the same Broker-owned plaintext vnode and content truncation policy as descriptor-based truncation, preserving the inode and the new length visible through already-open descriptors; it does not publish a separate whole-file replacement.

The controller derives the runtime cipher key with PBKDF2-HMAC-SHA256 and 100,000 iterations once per sandbox startup; injected descendants receive only the derived 32-byte key, so each exec does not repeat PBKDF2 or inherit the passphrase and salt as runtime configuration. Version 1 of `.key.json` implies those KDF parameters. Its version field is the compatibility and migration boundary for any future KDF change; an existing workspace must never silently switch parameters. Directory paths remain mirrored. For each encrypted business file or symlink, the original logical leaf bytes are authenticated-encrypted with AES-256-GCM under a filename-specific domain and encoded as an `enc_` URL-safe token. Ciphertext tokens of at most 255 bytes are both the physical leaf name and the parent `.metadata` record key. Longer ciphertext uses `enc_long_<SHA-256>` (URL-safe Base64 without padding) as both names, with the full authenticated ciphertext in that same record's `encrypted_name` field. The decoder verifies the digest and authenticates the ciphertext before using the logical name. Logical leaf names may be up to 255 bytes. There is no independently generated random alias, `backing_names` map, or persisted plaintext logical-name field. Write leases use a fixed-length SHA-256 digest of the physical leaf, shared by ordinary publication and key migration, so adding the lease prefix cannot exceed NAME_MAX. Filename encryption uses a fresh nonce, so recreating the same logical name may produce a different ciphertext token without introducing an unrelated backing name. Plain-mode entries and controller-managed executable caches retain literal logical names, with reserved prefixes escaped losslessly. Physical business files beneath `<workdir>/fs` remain ciphertext while the sandbox is running. Lower files without an authoritative upper entry are opened directly from their host paths.

Encrypted upper opens use one anonymous, unlinked plaintext vnode per ciphertext backing inode. A separate authenticated local-filesystem Broker in the parent owns that vnode and the open ciphertext container; it is independent of the NFS Broker and starts only in encrypted mode. Every independent logical open receives a duplicate of the shared plaintext vnode, a separate anonymous state descriptor containing its logical offset and status flags, and a separately opened descriptor for one shared per-inode lock anchor. Descriptor duplicates and fork or exec descendants share the original open state, while a later independent open receives new state and reuses the inode vnode and lock anchor while that inode still has live handles or mappings. Final release drops per-open descriptors immediately; a later cold open can therefore materialize a new vnode. The hook implements `read`, `pread`, `readv`, `write`, `pwrite`, `writev`, and `lseek` against that state with positioned native I/O, so the kernel offset shared by duplicated vnode descriptors is never application-visible. The open-state descriptor combines a process mutex with a cross-process record lock to preserve offset and flag ordering after `fork`. Sequential reads and writes hold that state through the operation; positioned reads and writes only snapshot the status flags under the lock and release it before IPC and native I/O, because they neither consume nor update the shared offset. Append selection and encrypted Begin/Finish coordination retain their existing backend boundaries. The lock anchor gives independent opens the same `fcntl` and `flock` locking identity without exposing a plaintext path. Before a record-lock call reaches the anchor, `SEEK_CUR` and `SEEK_END` are normalized against the logical open offset and file length; lock access modes are checked against the logical descriptor. Native blocking lock waits run without a Rust guard. Independent ordinary writes may overlap on the shared vnode as they can on a native file. Broker-side per-inode coordination is exclusive only where the emulation requires it: append EOF selection, lazy materialization, and truncating a live shared open. Ciphertext publication remains serialized by the Broker's shared-file mutex. The shared vnode makes completed writes and shared mappings immediately visible to every open and avoids repeated decryption or peer-snapshot copying.

Before a non-empty intercepted write or truncation mutates the plaintext vnode, the hook synchronously sends `BeginWrite`; append uses `BeginAppend`, which exclusively reserves the current shared EOF and returns it as the write offset. A successful begin promotes that fresh authenticated UDS connection into an operation-scoped write lease. Native plaintext I/O then runs while the connection remains open, and the matching `FinishWrite` or `CancelWrite` must use that same connection and consumes the lease. Multiple ordinary `BeginWrite` reservations may coexist, while append, lazy materialization, and truncating a live shared open report temporary `EAGAIN` contention and are retried within the client's bounded readiness deadline. After native plaintext I/O, `FinishWrite` records only the completed range; an interrupted or failed native operation sends `CancelWrite` and is not treated as completed. EOF before either terminal request identifies exactly one abandoned reservation. If every pre-existing byte in that reservation was resident when it began, the Broker conservatively schedules the current vnode range for writeback. If a reservation included unmaterialized pre-existing bytes, the Broker cannot distinguish an unwritten sparse zero from application data: it preserves the last valid ciphertext, poisons and detaches the old plaintext vnode, returns `EIO` for later Broker operations on old handles, and lets a new independent open construct a fresh vnode from ciphertext. This recovery may lose an abnormal process's unconfirmed write but never publishes guessed plaintext over authenticated data. A synchronization request does not wait for or fail solely because an ordinary write is still in progress: it flushes ranges that were completed before the Broker takes its shared-file snapshot, and a later `FinishWrite` registers the entire actual range for a subsequent writeback. This matches native concurrent write/sync semantics without exposing the authenticated container to concurrent Broker mutation. Completed ranges for one vnode may coalesce for at most ten milliseconds before the Broker encrypts the affected blocks and logical length. If the completion response cannot be confirmed after native success, closing the operation connection triggers the same lease recovery; the hook also retains the completed range in its local dirty set so a later explicit synchronization or close reports or repairs a recoverable writeback failure without retrying the application write itself. A final descriptor close first sends `PrepareClose` to synchronize while retaining Broker ownership, then calls native close, and releases that ownership only after native close succeeds. Synchronization or native-close failure leaves the registration and Broker reference usable for retry. `fclose` flushes before managed cleanup and releases ownership once libc has consumed the stream, even when libc reports a flush error. An encrypted descriptor opened with `O_SYNC` or `O_DSYNC` performs durable Broker synchronization after each successful non-empty write and returns an error if that synchronization fails; both flags use a full encrypted-container sync because authenticated content length and generation metadata are required for recoverability. Every Broker control request carries a random request ID. Ordinary ambiguous transport failures retry the same ID, and the Broker waits for an in-progress duplicate or replays its bounded 120-second result. An operation-scoped begin is not transport-retried after an ambiguous failure; its connection EOF releases or isolates the reservation, while service-level `EAGAIN` retries use a new connection and request ID within the readiness deadline. An open response must be claimed, and an unclaimed response is aborted on expiry instead of leaking descriptors. Fork and `posix_spawn` retains are acquired in the parent before native child creation for the exact advertised Broker-handle set, including close-on-exec and mapped-only handles. Fork failure releases its retain, and spawn failure performs an explicit synchronous release; a release failure fails the spawn instead of being hidden by destructor cleanup. A successful child adopts a retained handle only when at least one content alias and its state and lock descriptors still pass physical-identity and role validation after spawn file actions. If every alias was closed, close-on-exec, or replaced, child initialization releases that handle immediately. Successful exec also releases advertised mapped-only handles because the new image does not inherit mappings; failed exec keeps the old image's ownership. Matching but unadopted internal content, state, and lock descriptors are closed, while a replacement descriptor whose physical identity does not match is left to the application. Final release removes closed handles immediately instead of retaining their file descriptors in a replay cache. Only the existing bounded request-result cache replays completed request IDs; closed handle IDs cannot be reactivated. Existing containers retain their physical inode during block updates and truncation, while namespace creation uses the overlay's lock-serialized publication flow. Direct host reads of upper storage therefore see only ciphertext, while hooked processes share one coherent plaintext vnode.

The root `.fs.lock` gives one runtime exclusive ownership of a work directory and excludes key migration. The SDK's `Sandbox::run` owns it for one command. Overlapping CLI `run` invocations with the same canonical workdir, build, and effective configuration instead join one ephemeral per-workspace session daemon, which holds the lock and shared controllers until the final command releases its lease. A mode-0600 startup lock at `<workdir>/runtime/session-start.lock` elects that daemon and remains inherited for its lifetime; the owner-only session socket uses a short SHA-256-derived name below `/tmp/agora-sandbox-session-<uid>`. Different effective configuration or build identities are rejected rather than sharing runtime credentials. Join plus executable preparation, cancellation, and final release each use one absolute 60-second client control deadline across their framed writes, reads, reconnects, and retries; the launched child itself has no session-imposed runtime deadline. An idle daemon with no accepted lease retires after reporting an incompatible build, allowing that same client invocation to wait for the startup lock and replace it. A daemon with an active lease rejects the incompatible build without interrupting the existing process tree. `.vfs.lock` serializes short overlay metadata and publication transactions across every process in that runtime. A fork-aware per-process pool reuses unlocked descriptors for sequential transactions, opens distinct descriptors for overlapping transactions so advisory locking still serializes threads, and discards inherited pooled descriptors after a PID change. The same file stores an eight-byte metadata publication generation. One transaction lazily reads that generation once and reuses the snapshot for all metadata, marker, and reconciliation work under the VFS lock; a generation update inside the transaction refreshes the snapshot. Transaction-external queries still read the shared generation directly. Per-process metadata caches compare that generation, including cached absence, so a publication by another sandbox process invalidates stale directory state without reopening every `.metadata` file. Both present and absent directory cache entries share a 1024-entry bound. Read lookups share immutable `Arc` snapshots instead of cloning an entire directory; mutations use copy-on-write so an existing reader's snapshot cannot change. Cached directories also retain the physical marker identity; a marker removed or replaced outside the sandbox invalidates the local cache and advances the shared generation. Batched record lookup deduplicates the requested ancestor closure and reconciles each reachable path once. When an ancestor has no reachable upper directory and marker, deeper upper records are untrusted and skipped; an encountered whiteout still rejects requested descendants. Validation remains lazy and startup does not recursively scan the upper tree. A writable encrypted backing identity holds a shared namespace lease that records its currently attached ciphertext destination. Writers do not block one another at the namespace layer or for ordinary plaintext vnode writes; the Broker serializes encrypted-container publication and the operations that require exclusive emulation. Regular-file rename moves and retargets the source lease so its open handles continue writing to the renamed path; handles for a replaced target become detached. Unlink removes the current lease sidecar and detaches existing handles, whose later writeback is ignored instead of recreating the name. Directory rename still takes non-blocking exclusive leases for affected subtrees and returns `EBUSY` while an affected writable handle remains attached. Different work directories are independent.

A write ID can own at most one live operation-scoped lease. Request-level replay is handled only by the request-ID response cache and cannot create a second lease owner.

## Copy-On-Write View

The VFS owns path normalization, physical-name encoding, lower-layer reads, whole-file copy-up, whiteouts, per-directory metadata, encryption, lock-serialized publication, and logical owner/group/other authorization. Each authorized VFS operation resolves paths, checks the operation-specific permissions, and stages or applies its namespace change through one scoped overlay transaction and one `.vfs.lock` snapshot. Within that transaction, final-follow operations reuse the resolved logical endpoint for attribute checks, and ancestor search returns the immediate parent's effective attributes for a later parent write check; neither endpoint nor parent is resolved a second time. Descriptor metadata operations compare the opened backing device/inode with the currently visible object inside the same overlay transaction. A renamed or replaced path cannot redirect an old descriptor's mode or timestamp update to another object. The hook is an adapter for libc operations, credential selection, descriptor tracking, and audit events; it does not calculate overlay or mode-bit policy or pre-authorize a later VFS mutation. Open remains two-phase: authorization and staging share the first transaction, a per-file lease protects the staged backing while native descriptor construction occurs without the namespace lock, and a short second transaction publishes `cow` only after descriptor construction succeeds. In plain mode that lease is released after publication; in encrypted mode it remains attached to the shared Broker vnode. Reconciliation does not discard an unrecorded upper object while its staging lease is active, so another concurrently entered CLI process cannot treat a just-created upper file as an external artifact. Failure still drops the staged state without publishing metadata.

Reads prefer an authoritative `cow` upper entry and reject a `whiteout`. Otherwise a lower file or directory is opened directly from its host path without copying it, creating upper directories or metadata, or passing it through decryption. Read-only regular opens and stat-family calls use the native host operation directly when the requested path, its resolved symlink target, and their ancestor chains have no overlay entry-state override. A logical-attribute override on the endpoint still requires full VFS metadata patching; an allowed ancestor attribute override does not disable the native metadata fast path after its execute/search permission has been checked, while a denied ancestor does. Mutating and special-flag operations continue through the full VFS path. A `cached` entry is non-authoritative and is reserved for explicit materialization such as executable preparation or a staged mutation; normal reads continue to use lower until the mutation commits as `cow`. A later staged write refreshes stale cached data when the lower checksum changes. Source-derived cached attributes refresh with that lower snapshot, while an explicit logical attribute override remains authoritative across copy-up and a failed native open. Cached lower MD5 values used by ordinary copy materialization and prepared executable validation are change detectors, not security primitives.

A successful write-intent open changes an entry to `cow`. Existing lower data is copied up first; newly created data exists only in the upper tree. An encrypted `O_CREAT|O_EXCL` open reserves the logical leaf's encrypted ciphertext token while holding `.vfs.lock`, so another VFS cannot create the same logical path before the first open commits; abandoning the staged open removes the reservation. Permission failures are rejected before copy-up; a later native open failure leaves any staged cache entry non-authoritative. COW entries are never refreshed from the lower path.

Before using upper state, the VFS reconciles it while holding `.vfs.lock`. A `cow` or `cached` record whose physical backing object was removed outside the sandbox is deleted together with its logical attributes, encrypted-name reservation, and attached write lease, after which lookup falls through to lower. A `whiteout` remains authoritative when no backing object exists; an unexpected object at a whiteout path is removed without clearing the whiteout. An attribute-only lower override remains valid without upper data. An unrecorded upper file or symlink is removed, and a physical directory without its own marker is removed recursively even when a descendant marker looks valid. Removing a whole upper directory outside the sandbox therefore makes the next access use lower in the same running process. A successful managed directory rename retargets the calling process's tracked logical cwd, including descendants. Before any intercepted spawn or exec, an invalid native cwd is re-resolved from the tracked logical cwd through the same reconciled view and moved to its current NFS, upper, or lower representation. If that logical directory no longer exists or cannot be authorized, child creation fails closed instead of inheriting an unlinked cwd and resolving later relative paths outside the managed view. Cleanup failure aborts the operation instead of exposing a partially reconciled view, while invalid JSON in an otherwise continuous marker chain remains a hard error.

Deletion records a `whiteout`, hiding any lower entry with the same logical path. Unlink and rmdir publish that authoritative whiteout directly in one parent metadata publication and then remove upper data and a regular-file write lease idempotently. Rename validates POSIX type, descendant, non-empty-directory, and materializable-file constraints before copy-up, preserves ordinary symlinks when materializing a lower directory, and then directly renames upper state while holding `.vfs.lock`. It retargets a regular-file write lease and updates logical metadata after the physical rename. Source whiteout and destination `cow` are published together when both names share a parent, while cross-directory rename publishes one marker per parent. Case-only rename compares exact directory-entry spelling in addition to inode identity, and renaming between hard links to the same inode is a no-op. Namespace operations do not maintain a journal, backup, rollback transaction, or abnormal-exit/power-loss recovery guarantee; a process or storage failure between their physical and metadata steps may leave state that must be reset by deleting the affected upper workspace outside a running sandbox. Special files that would require copy-up fail without leaving staged upper data. Before VFS lookup, the hook normalizes logical absolute paths and checks the effective native-passthrough roots received from the runner. The unconditional `/dev` root and every configured root, including its resolved existing-ancestor alias such as `/private/var` for `/var`, bypass COW lookup, metadata overrides, backing-path rewriting, encryption, descriptor/directory tracking, and filesystem audit for every covered path- or descriptor-based filesystem operation. Configuration roots must be absolute; validation rejects overlap with the sandbox work directory or an NFS logical root, and the normalized configured set participates in CLI session identity. Component matching excludes sibling prefixes such as `/developer`, and normalization prevents `..` escapes from a configured root. Relative `*at` paths are classified only after resolving their directory descriptor. Native kernel permissions and errors are authoritative on that branch, and write opens such as `/dev/null` never create COW metadata. Operations with two filesystem operands delegate to native libc only when both operands resolve inside the allowlist; a rename crossing the allowlist boundary fails with `EXDEV`, while unsupported link/clone/copy families retain `ENOTSUP`, so an allowlisted operand cannot expose another host path. Intercepted non-allowlisted `opendir`/`fdopendir` plus `readdir`/`readdir_r` enumeration merges NFS, upper, and lower names when an NFS route applies, otherwise upper and lower names only. It prefers NFS over upper and upper over lower, filters overlay whiteouts from the overlay portion, decrypts encrypted logical names, and hides controls. During managed macOS FTS traversal, interposed `getattrlistbulk` synthesizes that same merged view so system tools receive NFS and upper-only files as well as lower entries; `fts_children` and `fts_read` additionally filter whiteouts, repair synthetic metadata where libc reports `FTS_NS`, patch encrypted-file stat records with plaintext sizes and logical attributes, and present logical paths and names instead of backing paths. Native caller comparators receive temporary entries containing those logical paths and names, never ciphertext backing names. `rewinddir` rewinds every contributing stream and resets merged-view deduplication. `fdopendir` retains the descriptor's actual layer when the view changes after `open`; it opens any complementary layers before transferring descriptor ownership, so preparation failure leaves the caller's descriptor open.

Each directory's `.metadata` is versioned JSON. Version 3 has one `entries` record map; each record may contain entry state and logical attributes. For encrypted business files and symlinks, the record key is always the physical leaf name: either the authenticated filename ciphertext or its bounded long-name digest as described above. Only long names include an `encrypted_name` ciphertext field; plaintext logical names, `backing_names` and `name` fields are not persisted. This extends version 3's record without a second storage path or additional control file. Plain-mode entries and controller-managed cached executables or loader images use literal UTF-8 record keys; non-UTF-8 bytes and names beginning with reserved `base64:` or `enc_` prefixes use `base64:<URL_SAFE_NO_PAD>`. The decoder can still read versions 1 and 2 when directly encountered, but normal startup neither recursively scans nor rewrites legacy metadata and compatibility with those legacy formats is not guaranteed; the supported upgrade from them starts with a fresh `<workdir>/fs`. Existing version-3 short-name records remain readable without rewriting for the long-name extension. Entries are `cached`, `cow`, or `whiteout`; non-authoritative cached entries carry a materializer type and source identity. Ordinary copy materialization additionally carries a lower MD5, executable materialization carries the prepared output MD5 and target platform/architecture variant, and application loader materialization carries the byte-for-byte copied image MD5. Normal VFS reads continue to select lower content for executable and loader cache records until an ordinary sandbox mutation commits a `cow` entry. Logical mode, owner, group, and access/modification times are stored in the same record and remain separate from physical ciphertext attributes. A directory marker is limited to 64 MiB, 100,000 records, and 4096 bytes per stored record name. Encrypted write-lease destinations are limited to 16 KiB. `.key.json` is limited to 64 KiB; `.rekey.json` is limited to 64 MiB, 100,000 entries, and 16 KiB per encoded path. Readers enforce the byte limit before allocation and again while reading, so concurrent growth cannot create an unbounded allocation. While holding `.vfs.lock`, general metadata updates truncate and rewrite the existing marker inode; a new whiteout record uses a validated append fast path and one cached descriptor so recursive deletion does not repeatedly serialize, reopen, or replace the growing marker. Every successful update advances the generation stored in `.vfs.lock` and updates the process-local cache. Metadata updates deliberately do not use a temporary file, journal, file sync, or parent-directory sync and therefore guarantee visibility to running processes, not persistence across abrupt process termination or power loss. Ciphertext and key-migration publication retain their separately documented synchronization behavior.

## NFS Roots

The source module named `nfs` owns protocol-backed filesystem roots; the name describes Agora's generic network-filesystem layer and does not require the NFS wire protocol. `nfs/backend/mod.rs` defines the protocol-neutral backend trait and error boundary, while protocol-specific implementations live in private child modules. SMB2/3 is the first implementation and lives in `nfs/backend/smb/`; its storage type, sessions, path mapping, and protocol error adaptation are not visible outside that module. The existing `SmbRemoteConfig` public API is defined there and re-exported through `nfs` and `runner` without exposing the implementation module. The generic Broker and controller depend only on the storage trait. Later protocols must implement the same storage boundary instead of adding protocol logic to the hook or leaking implementation types into the generic NFS layer.

The CLI reads remote roots from the unified run configuration's `filesystem.nfs` array. An SMB
entry has `type: "smb"`, a logical `dir`, a `server` URI, and optional `username` and `password`.
The URI grammar is `smb://host[:port]/share[/remote/path]`; credentials in the URI, query strings,
and fragments are rejected. IPv6 literal endpoints, bracketed or unbracketed and with or without an
explicit port, are rejected because the current SMB backend cannot construct a valid TREE_CONNECT
service name for them; hostnames remain accepted even when DNS may resolve them to IPv6. The SDK
equivalent remains `SandboxConfig::with_smb_remote`, whose
typed configuration also supports an SMB domain. Logical roots must be normalized absolute
non-root paths and may not overlap another NFS root, `/dev`, or any part of `<workdir>`; validation
also compares existing canonical ancestors so a symlink alias cannot bypass those boundaries.

```json
{
  "tls": "off",
  "filesystem": {
    "local": { "encrypt": "plain" },
    "nfs": [
      {
        "type": "smb",
        "dir": "/network/team",
        "server": "smb://files.example.com/documents/projects/current",
        "username": "alice",
        "password": "secret"
      }
    ]
  }
}
```

An NFS root contributes the highest-priority namespace layer, so lookup order is `NFS > upper > lower`. An existing NFS entry wins over an upper entry, overlay whiteout, or lower entry with the same logical name. An NFS `ENOENT` falls through to the normal overlay lookup; any other NFS error fails the operation instead of silently exposing another layer. Directory enumeration merges all available layers and emits each logical name once with the same priority. Each configured root is also injected as a synthetic directory entry into its existing logical parent for both ordinary and managed FTS enumeration, without creating a host or upper placeholder; it hides a same-named local entry and remains visible while its backend is unavailable, while access still reports the backend error. Removing an NFS entry therefore reveals an existing upper/lower entry immediately, while removing a path absent from NFS applies normal overlay deletion. Existing fallback entries retain normal COW and encryption behavior. A create under an NFS route uses an existing visible upper/lower entry when one exists, but a path absent from every layer is created directly in NFS.

Remote objects themselves bypass COW storage, filename/content encryption, whiteouts, and `.metadata`. The runner does not mount the share in the host namespace. Instead, a per-run parent-process Broker owns credentials and one backend session holder per configured root. After the Broker is ready, its controller starts one independent connection probe per root without awaiting those probes before spawning the child. The logical root leaf is synthetic, but its parent must already be visible as a directory in the local overlay when the probe starts; otherwise the route reports `ENOENT` or `ENOTDIR` without attempting an SMB connection. For an SMB share URL with a configured subpath, the probe also stats that subpath and reports success only when it exists as a directory; a pure share root needs only a successful share connection. A successful probe retains the established backend session; a failed probe leaves the holder available for a later filesystem access to retry normally. Each completed probe becomes a controller status event, and the runner writes one sanitized structured `nfs` log record containing the route, status, logical root, endpoint, and failure errno when applicable, but no username or password. The record uses the same logger and destination as CLI audit records and never enters child stdout. Probe failure neither terminates the Broker nor the child. Every `filesystem.nfs` array entry receives a stable route index, so one run can expose multiple independent SMB roots. The injected hook receives only normalized logical routes plus a per-run authenticated Unix socket; endpoint, share, username, domain, and password never enter the child configuration. Remote protocol version 9 supports authenticated persistent control streams, direct positioned range I/O, append-at-current-EOF writes, resize, open-handle metadata refresh, range-aware snapshot materialization, writable-mapping registration, and dirty-range synchronization. An authenticated `ping` converts one connection into the inheritable multi-request fallback used when a nested kernel sandbox denies a new Unix connection. The socket, opaque empty metadata anchors, and unlinked payload or snapshot files live in a mode-protected short temporary directory under `/tmp` and are removed with the run. Named anchors contain neither a remote name nor file content. Stat and list responses create fresh anchors rather than caching one per remote path; the hook owns each claimed anchor through a short RAII lifetime, and unclaimed response resources expire from the Broker cache. NFS opens and closes still use the normal filesystem audit channel.

A regular-file open retains one backend file handle and returns a correctly sized sparse anonymous descriptor without downloading file content. Interposed scalar and vector `read`, `write`, `pread`, and `pwrite` operations transfer at most 64 KiB per syscall request through unlinked descriptor payloads; content is never embedded in the JSON control frame. Reads fetch the requested remote range, and successful writes reach the persistent backend handle before the syscall returns. A successful direct write or truncate remains successful even if the best-effort resize of its anonymous placeholder fails, because the remote handle is authoritative. `O_SYNC` and `O_DSYNC` direct writes additionally issue backend FLUSH before returning; after a handle transitions to snapshot mode, the same flags publish the changed snapshot before a successful scalar or vector write returns. `fsync`, full-sync `fcntl`, pre-exec flush, and last tracked close issue backend FLUSH rather than downloading or replacing a direct-mode file. `ftruncate` and path truncate resize the persistent handle directly. Within one process, descriptor aliases share one tracked registration and the native anonymous descriptor's open-file offset; the registration lock orders sequential `read`/`write` and append calls, while `pread`/`pwrite` leave that offset unchanged. Direct-mode `SEEK_SET` and `SEEK_CUR` remain native; `fstat` and `SEEK_END` refresh metadata through the persistent backend handle so an external size change is visible without reopening. Append uses the descriptor's current status flags, including changes made through `F_SETFL`, and refreshes the server-reported length while holding the Broker's per-root mutation lock; an external SMB client that ignores that cooperative ordering can still race the length query and write. Each write payload carries its length and MD5 in the idempotent request fingerprint. MD5 detects a mismatched or changed retry payload and is not a cryptographic integrity boundary. Existing-file `O_TRUNC` is deferred until the normal open audit succeeds. A failed pre-registration create is removed only when the backend CREATE response proves that this open created it and the path still has the same identity, so an external racing create is not deleted. An `fopen` that receives an anonymous managed descriptor fully materializes that descriptor before handing it to libc stdio; this preserves native buffered `FILE` semantics even when libc performs internal I/O that does not bind through the public `read` or `write` symbols. This compatibility path has whole-file first-open cost, while ordinary `open` plus scalar/vector I/O retains direct range transfers. For a non-empty write-only stdio snapshot, the Broker opens a separate internal read-only handle and validates its identity against the existing open baseline before and after reading. It closes that extra handle on success or failure; application FD access flags and ordinary write-only remote opens remain unchanged. A server ACL that forbids reading the old contents still rejects this snapshot path with a permission error; the implementation does not grant extra remote authority or return an incomplete snapshot.

Operations that require the kernel to access file data without a later intercepted scalar/vector call transition the open handle from direct mode to a sparse anonymous snapshot. `mmap`, `aio_read`, and `lio_listio` reads materialize only their declared file ranges; mmap uses the exact mapping range, while later scalar and vector snapshot reads share the local encrypted path's adaptive 16-256 KiB read-ahead policy. The Hook and Broker use the same byte-range set implementation to cache successful local and remote materialization and avoid downloading overlapping ranges twice. The persistent backend handle remains open while the snapshot is partial. Ambiguous operations such as `sendfile` with headers, `fcopyfile`, guarded or asynchronous writes, `SEEK_DATA`, and `SEEK_HOLE` materialize the missing remainder before native access. `MAP_PRIVATE` modifications never write back, and a clean partial snapshot closes without downloading its unobserved ranges.

Before a writable-descriptor `MAP_SHARED` mapping succeeds, the Hook registers its complete file
range as potentially writable regardless of the mapping's initial page protections. The remote
Broker fingerprints only newly registered, already materialized ranges with a fixed-size streaming
buffer and retains those baselines across intermediate synchronization. At `msync`, mapping
teardown, descriptor sync, pre-exec flush, or normal last close, native `msync` first exposes mapped
pages through the shared anonymous vnode and the Broker compares the registered ranges. An
unchanged mapping performs no publication and therefore does not conflict with a newer external
remote version; a same-size modification is detected even when the process never called `msync` or
`munmap` before normal exit. `MAP_PRIVATE` mappings are never registered or published.

Native snapshot writes report their completed byte ranges, while writable mappings use the Broker-owned range fingerprints above. Those ranges are already valid local plaintext and are never overwritten by deferred remote reads. Before publishing a changed snapshot, the Broker downloads only still-missing bytes from the opened baseline up to the resulting logical length, closes the persistent backend handle, computes MD5 with a fixed-size buffer, and uses whole-file optimistic CAS. Truncation is detected from the anonymous descriptor length. A snapshot that was fully materialized before native access retains checksum-based fallback detection for interfaces whose completed range cannot be observed precisely. The SMB backend streams range downloads and snapshot uploads in fixed-size chunks instead of constructing a whole-file `Vec`; clean read-only or private mappings therefore use staging space and network transfer proportional to the accessed ranges, while changed snapshots still require a complete local baseline and whole-file upload. It queries the opened object's identity before and after each deferred range transfer and rejects a changed object with `ESTALE` rather than exposing mixed-version contents; impossible advertised lengths, premature EOF or empty responses, and responses larger than the requested or remaining range fail as protocol errors. Writeback acquires a deterministic cooperative sibling lock, creates an opaque randomly named sibling, writes its complete contents, sets its length, flushes and closes it, then opens the current target and verifies its baseline identity. A mismatch returns `ESTALE`; otherwise one SMB rename atomically publishes the staged file. The cooperative lock provides strong CAS between Agora writers; external clients that ignore that lock can still replace the target between verification and publication, so their detection remains best effort. Failures attempt to remove the staged sibling, and a transport ambiguity drops and reconnects the backend session before retrying the same staged operation; the original target is never left partially overwritten. An unreachable share or process crash can still leave an opaque staging or lock file for external cleanup. Only exact `.agora-write-<32 lowercase hex>.tmp` and `.agora-lock-<32 lowercase hex>.lck` leaf names are reserved: directory listing hides them and direct public storage operations reject them, while similarly prefixed business names remain visible and accessible. Ordinary SMB rename retains replace-if-exists semantics for both files and directories and reconnects before resolving an ambiguous transport result from observed namespace state. Rename detaches a replaced destination handle before retargeting open source descendants. Unlink detaches matching open handles, and later sync or close does not recreate the removed path.

Selected NFS directories use synthetic logical views backed by opaque empty anchors for `stat`, `opendir`/`fdopendir`, `readdir`, relative `*at` operations, current-directory operations, and managed FTS traversal; overlay directory streams are attached to that view when fallback layers also exist. A successful remote `chdir` keeps the native process cwd on its opaque anchor and tracks the logical NFS path. Intercepted `posix_spawn` and `exec` calls replace any caller-provided remote-cwd variable with that tracked path. A new hook runtime restores it only when the inherited native cwd is a valid anchor beneath the configured Broker runtime and the logical path still belongs to a configured route, so external commands launched after `cd` retain the same logical directory without exposing the runtime path. `mkdir` creates in NFS only when the name is absent from every layer. Unlink/rmdir removes the selected NFS object first and otherwise delegates to overlay deletion. A rename whose source is selected from NFS is sent to the backend; a source selected from upper/lower remains an overlay rename when both operands stay in the same NFS route and no NFS destination shadows it. A rename crossing NFS roots or crossing between an NFS route and host/COW paths returns `EXDEV`; the configured root itself cannot be removed or renamed. Regular NFS files are presented as non-executable mode `0666`, directories as `0777`, and owner/group as the effective process identity; regular-file `X_OK` fails. Symlink, hard-link, ownership, mode, timestamp, flags, xattr, clone, and copy mutations are not currently represented by the backend trait and return `ENOTSUP` for a selected NFS object rather than mutating a same-named fallback object.

Content-mutating `fcntl` commands on a direct or snapshot remote descriptor return `ENOTSUP` instead of mutating only its anonymous local placeholder.

This is a hybrid userspace client, not a mounted kernel shared-inode implementation. Direct handles expose backend range I/O and write-through visibility; snapshot handles retain whole-file optimistic coherence, so two changed snapshots of the same baseline conflict after the first publication and an unchanged snapshot never overwrites newer remote data. Each configured SMB root owns four lazily connected session slots selected in round-robin order for path operations. An opened SMB handle remains pinned to its selected slot and session generation for its lifetime. Operations on different slots can proceed concurrently; one slot's reconnect invalidates only handles pinned to that slot, while an explicit root reset invalidates every slot. Broker namespace and snapshot-publication mutation locks remain root-scoped, so the pool increases independent stat, list, direct-read, and direct-write concurrency without weakening rename or optimistic-CAS ordering. Every request carries a random request ID. The hook retries an ambiguous transport failure with the same ID, while the Broker executes the operation once, waits for an in-progress duplicate, or replays the completed response. Resource-bearing open, read, stat, and list responses require a follow-up claim; unclaimed handles, payloads, anchors, and list descriptors are reclaimed when the bounded response cache expires. Directory entries flow incrementally from bounded SMB query pages into an anonymous descriptor and are decoded with an independent positioned cursor, so no SMB page, generic Broker collection, or control frame must contain the full directory. A list is rejected with `EOVERFLOW` above 100,000 visible entries or a 64 MiB serialized payload; the hook checks both descriptor length and entry count before later validation allocations. A named anchor remains opaque but is padded to at least the logical basename byte length so Darwin FTS can substitute a longer logical name safely. A claimed list anchor is owned by an RAII guard before descriptor parsing, so malformed or oversized payloads remove it immediately. Close and abort retain bounded tombstones so retrying either operation is idempotent. A background connection-probe failure is informational; a backend/network failure during a covered filesystem operation fails that operation, and a Broker service failure terminates the run. The 8 GiB limit applies only when an operation requires whole-file snapshot materialization; larger files remain available to ordinary direct range I/O. The Broker gives each request one absolute 15-minute execution deadline across backend calls and checksum work, then attempts backend-session reset for at most five seconds and returns `ETIMEDOUT`; hook requests wait 15 minutes and five seconds per transport attempt. The controller separately bounds an incomplete initial request to one second and a blocked response to five seconds, while transport writes suppress `SIGPIPE`. Unsynchronized changes can still be lost on fatal termination, and sharing an inherited NFS descriptor between processes that continue after a non-exec `fork` remains outside the supported lifetime/coherence model.

## Hook Semantics

The pre-main Hook initializer hides consumed internal environment variables by replacing their pointer slots with empty, non-null strings. It must not compact the original Darwin `envp` array: Go and other runtimes locate the following Apple `executable_path` vector through the original `argv` layout. The same rule applies to the pending process audit context. Consumed keys remain absent from environment lookup, unrelated variables remain unchanged, and this startup-only operation adds no runtime environment hook or synchronization path.

Read-only Local Broker synchronization does not treat a ctime-only change as proof of a content write. When length and mtime remain unchanged, it compares already-resident plaintext ranges with their authenticated ciphertext before rejecting a changed snapshot; matching contents permit normal sync/close without decrypting lazy holes or rewriting ciphertext. Changed length/mtime, changed resident bytes, and caller-supplied dirty ranges still fail the read-only validation. Ordinary unchanged reads add no comparison pass.

A successful NFS rename to the same logical path leaves all open handles attached to the original object. The backend still validates the operation (including a missing source); the Broker skips only handle retargeting and must not treat this no-op as replacement of an open destination.

Ordinary encrypted-file reads execute directly against the shared plaintext vnode after any required
lazy materialization. A non-empty write uses the authenticated Local Broker control protocol to
register its reservation before native positioned I/O and to report the completed range afterward on
the same operation-scoped UDS connection. Connection EOF releases that reservation; an abandoned
lazy range whose prior bytes were not resident poisons and detaches only its old plaintext vnode so
the last valid ciphertext remains authoritative and a later independent open can recover from it.
There is no shared-memory mutation journal or one-way notification descriptor. Independent ordinary
writes may overlap, while the Broker exclusively coordinates append EOF selection, materialization,
and live truncation and serializes ciphertext publication. Completed dirty ranges belong to the
shared plaintext inode rather than an individual open handle, so synchronization through any handle
drains and flushes all ranges completed before that synchronization snapshot.

The compile-time `platform` facade selects the private platform hook implementation; it has no runtime dispatch or cross-platform hook trait. The current implementation lives under `platform/macos/hook`. Its `mod.rs` owns the dylib initializer, global initialized state, config/control/filesystem startup, filesystem exit-flush registration, and the generic errno setter shared by child domains. `control.rs` owns the workload-independent inherited execution, audit, local Broker, and remote Broker streams; crate-level `ipc` supplies their anonymous descriptor lock and per-stream thread serialization. `abi.rs` owns Darwin ABI declarations and architecture-specific symbol bindings, including the `$INODE64` FTS variants used on x86_64 and the distinct canonical and cancellation-safe `close` entry points. `filesystem/mod.rs` owns the filesystem facade, shared runtime, guards, path/audit adaptation, descriptor identity, configured native-passthrough roots, and preparation flows reused across libc operation families; its operation modules and C variadic shim are colocated under `filesystem/`. Every tracked regular-file open owns one `ManagedContent` value under `filesystem/content/`. This closed facade owns the common writable, materialized, dirty, mapping, synchronization, and finish lifecycle and dispatches storage operations through a private object-safe `ContentBackend` implemented by the plain, encrypted-local, and NFS adapters. `filesystem/content/policy/` owns the backend-independent read, positioned-write, append, logical-offset, synchronous-write, and mapping-access policies; each backend declares its read/write mode and implements only the storage primitives needed by that mode. The plain and encrypted adapters do not add facade-level mutation serialization; the NFS adapter alone retains an operation mutex for its direct-I/O and snapshot transition state. The adapters otherwise retain their storage-specific handles, consistency rules, and Broker calls. `data.rs`, `mapping.rs`, and `descriptor.rs` adapt Darwin scalar/vector I/O, mapped-memory, and descriptor ABIs to the facade without selecting a storage backend. `open.rs`, `metadata.rs`, `namespace.rs`, `unsupported.rs`, and `lifecycle.rs` retain their operation-family responsibilities. Paths deliberately excluded from tracking by the effective native-passthrough roots continue to bypass `ManagedContent`. `nfs.rs` adapts logical NFS roots to the authenticated remote Broker without containing backend protocol logic. Directory enumeration and current-directory operations live in `filesystem/directory/mod.rs`; Darwin FTS and virtual `getattrlistbulk` support live in its nested `fts.rs`. Parent-side encrypted content synchronization lives under the crate-level `filesystem/broker`, independently of the generic remote backend and Broker under `nfs`; the Hook content facade does not merge their protocols or persistence rules, and both use the crate-private descriptor-capable framing in `ipc`. The platform hook's `network/mod.rs` owns `connect`/`connectx` interception and network recursion/runtime state, with raw socket conversion in `network/socket.rs` and Security.framework trust interception in `network/trust/mod.rs`. Process execution interception and its tests live under `process/`. Narrow implementation dependencies are limited to native cleanup, logical stat patching for FTS, and the shared runtime's native-passthrough namespace helpers; POSIX content policy remains in `filesystem/content/policy`, while namespace, authenticated-container, and remote-consistency policy remains in the VFS, local encrypted Broker, or NFS Broker respectively.

The hook covers `open`, `openat`, `creat`, `fopen`, `stat`, `lstat`, `fstat`, `fstatat`, `access`, `faccessat`, `readlink`, `readlinkat`, `realpath`, `symlink`, `symlinkat`, truncate, deletion, ordinary rename, zero-flag `renamex_np`/`renameatx_np`, directory creation, current-directory operations, `opendir`/`fdopendir`/`readdir`/`readdir_r`/`rewinddir` enumeration, macOS `fts_open`/`fts_children`/`fts_read`/`fts_close` traversal and its `getattrlistbulk` enumeration, `write`/`pwrite`/`writev`/`pwritev` including Darwin non-cancel variants, `aio_read`/`aio_write`/`lio_listio`, `mmap`/`msync`/`munmap`, `fork`, `close`, `fclose`, `fsync`, `dup`, `dup2`, and relevant `fcntl` operations. `mprotect` remains a native libc operation and never enters the filesystem runtime. Before entering the generic Rust filesystem guard, the mapped-memory interposers classify requests through an atomically published mapping-range snapshot and a fixed-size tracked-descriptor bitmap rather than locking the authoritative mapping or descriptor tables. Requests proven not to reference tracked state delegate directly to libc; descriptors outside the bitmap's range conservatively enter the managed path and consult the authoritative table. Managed descriptor and mapped-memory operations acquire one fair per-runtime resource lease that atomically covers the relevant descriptor registry, mapping registry, descriptor numbers, and address ranges. Compatible shared or disjoint operations proceed concurrently, while conflicting operations wait without allowing a later conflicting request to bypass an earlier one. Each operation reclassifies while holding its lease and keeps the kernel operation and corresponding state change within that lease; descriptor-table publication participates in the same coordination. A mapped-memory request already classified as managed returns `EAGAIN` without executing the native operation if the configured runtime or filesystem guard becomes unavailable. Native routing before the hook initializer completes is bootstrap behavior only; a configured initialization failure still terminates the child with status 126. The macOS `removefile` and `removefileat` APIs are also interposed but fail closed for managed paths because their secure-erasure semantics cannot be represented by the overlay. Relative `*at` operations resolve tracked directory descriptors through logical paths, including duplicated descriptors; successful close removes directory tracking immediately, while encrypted file state remains tracked until its last descriptor and mapping reference is gone. `realpath` resolves visible upper and lower components and symlinks but returns only the canonical logical path; both caller-provided buffers and libc-allocated null-buffer form are supported. Directory creation checks searchability and an already-visible endpoint before parent mutation permissions, so BSD `mkdir -p` receives `EEXIST` for an existing prefix. `fchdir` resolves the descriptor's logical path before changing the native current directory and fails closed when that resolution is unavailable. Successful local `chdir` and `fchdir` calls resynchronize the tracked path from the native current directory, translating a prepared upper directory back to its logical path and collapsing host aliases such as `/tmp` and `/private/tmp`; remote directory changes retain the logical NFS path and propagate it through the protected child runtime environment described above. Managed FTS streams force `FTS_NOCHDIR`, map prepared upper roots to logical presentation paths, and therefore do not perform per-entry current-directory resynchronization; untracked native FTS streams retain the defensive resynchronization path.

Encrypted upper regular-file descriptors refer to a shared anonymous plaintext vnode; direct lower reads retain native host descriptors. Each independent encrypted open virtualizes the caller's requested access mode, append/nonblocking/synchronous flags, and logical offset in its separate state descriptor. `dup`, `fork`, and exec inheritance retain that open-description state, while later independent opens do not share it. On macOS, guarded open, write, positional write, vector write, and close operations retain the caller's descriptor guard and pass through the same tracking and synchronization path as their ordinary counterparts. Broker-backed local plaintext descriptors start close-on-exec, but explicit `F_SETFD`, `dup`, `dup2`, and `F_DUPFD` operations retain native inheritance semantics so shell redirection can pass a descriptor to an external command; `F_DUPFD_CLOEXEC` remains close-on-exec. Before exec, the hook places only inheritable local content, state, lock, and Broker-handle records plus authenticated internal control descriptors in the protected child runtime environment. When a caller supplies macOS spawn file actions, Agora prefixes `addinherit_np` actions for the stable control descriptors and the then-inheritable local descriptor bundle during `posix_spawn_file_actions_init` instead of appending them after caller actions at spawn time. A later caller `close`, `dup2`, or `open` action may therefore deliberately replace a descriptor without producing a trailing inherit of an already-closed FD and `EBADF`. When the caller supplies no actions, Agora creates an internal action list containing the currently inheritable descriptors. The parent retains the exact encoded Broker-handle set before native `fork` or `posix_spawn`; native creation failure explicitly releases that retain. A successful child consumes only fully validated handles through the inherited close lifecycle, while initialization releases handles with no surviving valid content alias and closes matching unadopted internal descriptors. The new image validates the physical identities and roles of inherited content, state, and per-inode lock descriptors before restoring the per-open state, shared local Broker handle, and encrypted backing identity reported to the application. The control descriptors that remain available stay open across exec and share one unlinked anonymous control-lock file; a process-local mutex serializes threads and independent byte-range record locks serialize descendant processes without coupling different services. Acquisition has one 30-second deadline rather than waiting forever behind a stalled peer. A fresh control bundle authenticates every service before startup. A complete inherited bundle validates descriptor completeness, uniqueness, type, and peer identity, then reuses already-authenticated streams without redundant `ping` round trips; every real protocol request still carries its service token, and a transport failure reconnects through the fully authenticated fresh path or fails closed. Executable preparation and audit delivery prefer their inherited multi-request streams immediately. Local encrypted and NFS clients retain fresh-connection concurrency during ordinary operation and prefer the inherited stream after a PID change or when a fresh connection is unavailable. Local Broker protocol version 10 uses authenticated requests, an authenticated `ping` for a fresh multi-request stream, and a dedicated fresh connection for each `BeginWrite` or `BeginAppend` through its matching terminal request. Write leases never use the inherited multi-request stream because that stream is shared by unrelated processes. Anonymous remote data descriptors and local data descriptors without Broker support remain forced close-on-exec, and `F_SETFD` cannot clear that bit. Descriptor duplicates and writable `MAP_SHARED` mappings share one local Broker handle. Closing the last descriptor does not release that handle while a mapping remains, and a fork retains inherited local Broker handles in the child. `MAP_PRIVATE` mappings are never written back. Managed mapping records and partial unmap/fixed-replacement intervals use native page-rounded lengths. Read-only logical `MAP_SHARED` opens lower the new mapping's native maximum protection to exclude writes, so a later native `mprotect` cannot bypass the logical access mode; private mappings retain native writable copy-on-write upgrades. Every `MAP_SHARED` mapping backed by a writable descriptor registers its complete file range before native `mmap`, regardless of its initial page protections. Local synchronization first exposes native mapped pages, then uses the plaintext vnode identity to decide whether registered candidate ranges need encryption; candidate registrations survive intermediate synchronization. `msync`, `munmap`, `MAP_FIXED` replacement, path reopen, descriptor sync, exec, and controller shutdown flush mapped content, while `mprotect` remains entirely native. `open`, `stat`, `fstatat`, `access`, and `faccessat` follow the final logical symlink through overlay state unless no-follow behavior is requested, while `lstat`, `readlink`, `readlinkat`, and `AT_SYMLINK_NOFOLLOW` retain final-link semantics. The macOS-specific `O_NOFOLLOW_ANY` and `O_SYMLINK` modes return `ENOTSUP` before an encrypted open is staged. `stat`, `lstat`, `fstat`, and `fstatat` report logical attributes and plaintext file length instead of encrypted-container attributes when an upper entry or explicit logical permission override is active. For an encrypted upper regular file, path and descriptor metadata expose the same stable encrypted-backing device and inode rather than the anonymous plaintext descriptor identity. Untouched lower entries retain native host attributes. Create mode applies the child process's current umask and effective identity, and successful encrypted synchronization refreshes logical access and modification timestamps. Intercepted opens and mutations use effective credentials. `access` and `faccessat` use real credentials unless `faccessat` receives `AT_EACCESS`; invalid access-mode bits return `EINVAL`. All valid requests evaluate logical mode bits. Path operations also require execute/search permission on ancestors, and create/delete/rename operations require write plus execute permission on the affected parent directories. `O_NOFOLLOW` skips only the final symlink's access check and cannot bypass permissions on a regular final entry; `O_TRUNC` requires logical write permission even when combined with `O_RDONLY`. This is the classic owner/group/other mode model, not ACL, capability, sticky-bit, or identity virtualization.

When a nested macOS policy rejects a fresh connection to the Broker socket, the client creates a close-on-exec Unix `socketpair` and transfers the server endpoint through the already-authenticated inherited control stream. The controller admits that endpoint through the same bounded connection pool before acknowledging it, then processes `BeginWrite` or `BeginAppend` on the dedicated endpoint normally. The inherited multi-request stream therefore restores reachability without becoming the write lease or weakening EOF ownership.

For encrypted upper files larger than 1 MiB, a cold open without `O_TRUNC` validates the encrypted header and returns a correctly sized sparse anonymous plaintext vnode without scanning the body, including `O_WRONLY` and `O_RDWR` opens. Small files and truncating opens remain eager. Scalar and vector reads materialize the requested range with stateless adaptive readahead: four times the request clamped to 16-256 KiB, but never less than the request itself. Native writes populate their completed plaintext range directly; ciphertext writeback reads only that range and performs a 4 KiB ciphertext-block read-modify-write for partial boundary blocks, preserving both untouched plaintext ranges and sparse extensions without first decrypting the complete file. `mmap` materializes the requested mapping range before delegating to the native pager. Successful read, mapping, and write ranges are cached in both the Broker and each applicable open registration. `aio_read` and `lio_listio` reads materialize their declared offset and length, and `sendfile` does the same when no header or trailer makes its file-data length ambiguous. `aio_write` and `LIO_WRITE` on a Broker-managed local encrypted descriptor fail with `ENOTSUP` before native submission because Darwin AIO does not expose a synchronous completed-range boundary that can participate in the encrypted write reservation protocol. Untracked native AIO and NFS snapshot-backed asynchronous writes remain supported. `SEEK_DATA`, `SEEK_HOLE`, a read-only `fcopyfile` source, and ambiguous `sendfile` requests require full materialization because those kernel interfaces can observe the vnode without a subsequent intercepted read; `fcopyfile` into a managed local descriptor fails with `ENOTSUP` because it cannot report destination writes. Authentication failure in an untouched body block is therefore reported as `EIO` when that block is first materialized rather than during cold open. The v2 ciphertext format, 4 KiB authenticated blocks, shared-vnode writeback, and native mmap-after-materialization model are unchanged; unlike FUSE, page faults themselves do not call the Broker.

`chmod`, `fchmod`, and `fchmodat` require the effective UID to own an attached non-allowlisted logical entry or be UID 0, update logical overlay metadata, and never change lower host permissions. For an old descriptor whose logical path was unlinked or replaced, `fstat` no longer borrows the replacement's attributes. `fchmod` on a detached upper descriptor uses the original native descriptor; a detached lower descriptor returns `ESTALE` because its per-inode virtual mode is not retained independently of the namespace. This bounded fail-closed case must not chmod the host inode or replacement. Symlink creation records an upper COW link without changing the lower host; an absolute target that names a prepared path inside the private backing tree is translated back to its logical host path before storage, which keeps executable aliases usable. Content-mutating `F_SETSIZE` and `F_PUNCHHOLE` operations on tracked encrypted descriptors return `ENOTSUP` because they cannot currently report the affected plaintext range to the Broker. For non-allowlisted paths, ownership changes, hard links, `clonefile`, `copyfile`, `removefile`, `removefileat`, and `freopen` currently return `ENOTSUP` while the hook is active. Timestamp mutation (`utimes`, `lutimes`, `futimes`, `futimens`, and `utimensat`), file flags (`chflags` and `fchflags`), extended-attribute mutation (`setxattr`, `fsetxattr`, `removexattr`, and `fremovexattr`), and non-zero extended-rename flags also return `ENOTSUP` before touching the lower host. `freopen` is rejected before either the supplied stream or destination is touched. An allowlisted path or untracked descriptor resolved beneath any effective native-passthrough root is checked before these fail-closed cases and delegates to native libc, so the kernel's permissions and errno are preserved without VFS staging or audit. `posix_spawn_file_actions_addopen` supports read-only overlay paths; any non-allowlisted write, create, truncate, or append intent returns `ENOTSUP` without staging COW state. Direct syscalls, extended-attribute reads, and `seekdir`/`telldir` on merged directories remain outside the current hook surface.

The hook uses a thread-local recursion guard so VFS backing operations can call native libc without recursively re-entering the logical view. The filesystem and process guards check the process-wide initialized flag before accessing Darwin thread-local state, every ordinary filesystem-runtime lookup uses the same gate, and virtual `getattrlistbulk` checks the filesystem guard before consulting its FTS thread-local state; this keeps pre-initialization calls out of TLV and lazy-runtime bootstrap on both supported macOS architectures. The dylib initializer alone uses a separate direct runtime-construction entry point. Before entering the Rust filesystem guard, the ordinary and Darwin non-cancel scalar/vector, positioned/unpositioned `read` and `write` interposers classify the descriptor through the atomically published tracked-descriptor index. Descriptors proven untracked execute the corresponding native operation through a C shim with no active Rust filesystem guard while waiting on a terminal or pipe. Descriptors outside the bounded index conservatively enter the managed Rust path, but release the guard before a native scalar, vector, or seek fallback once the authoritative descriptor table proves them untracked. Tracked plain descriptors that need neither managed reads nor snapshot write tracking likewise delegate before acquiring content mutation/cursor state, and their blocking native I/O runs outside the filesystem guard. This includes tracked FIFOs whose reader must not hold the fork barrier while another thread forks.

The filesystem, process, and network guards defer catchable asynchronous signals and pthread cancellation before publishing thread-local state or acquiring Rust and pthread synchronization, while synchronous fault signals retain native delivery. Guard cleanup releases that state before restoring the caller's cancellation state and signal mask, so a pending cancellation or application handler that uses `siglongjmp` cannot abandon recursion state, a filesystem fork-barrier reader, a content mutex, or another Rust guard. Managed `readdir` and `rewinddir` keep their shared cursor state inside this filesystem guard, while an unmanaged directory stream releases the guard before calling native libc. Process-side reads of the tracked logical current directory also enter the filesystem guard before locking that state, so a concurrent fork cannot snapshot its mutex while another thread owns it. Audit connections and inherited control-stream transactions use the same ordering around their `RefCell`, process mutex, and cross-process record lock; protocol timeouts bound the latter transaction. Native path construction for `open`, `openat`, and path-backed `fopen` runs after managed path preparation releases the filesystem guard and re-enters it only to commit successful staged state; FIFO and slow-volume opens therefore retain native signal interruption. Native `posix_spawn`/`exec` and redirected `connectx` calls likewise run only after their preparation guard is released, preserving the caller's signal mask in a new image and keeping blocking native calls interruptible. Lock-descriptor translation is completed before native `flock` or locking `fcntl` waits. Trust-object preparation is protected, while the original Security.framework evaluator runs after that protection is released. Signal-mask setup or restoration failure aborts rather than silently weakening the fail-closed boundary.

Any filesystem call made recursively on that thread delegates to native libc, except a request already classified as managed mapped memory, which returns `EAGAIN` if it cannot enter the guard. Process execution remains fail-closed with `EACCES` when its guard cannot be entered. A process-wide `pthread_atfork` read/write barrier prevents `fork` from snapshotting an active filesystem hook and reinitializes that barrier in the child. The interposed `fork` defers asynchronous signals across its native call and restores the caller's mask in both returned processes, so an application non-local transfer cannot bypass the registered parent or child cleanup handler while the barrier is write-locked. If `fork` is re-entered while the forking thread itself owns the barrier's read side, the prepare handler temporarily suspends only that reader, drains readers on all other threads, acquires the write side, and restores the suspended reader in both the parent and child before the interrupted hook resumes; this avoids an unsupported read-to-write upgrade without weakening the cross-thread barrier. Thread-local destruction also releases a reader abandoned by a thread that exits before ordinary guard cleanup. The child handler resets only the process-local mutexes for inherited control streams; the parent-owned record lock remains the cross-process ordering boundary if another thread was inside a control transaction at fork. While the prepare handler owns that barrier, filesystem hooks invoked by an earlier-registered parent or child atfork callback on the forking thread delegate directly to native libc until the parent unlocks the barrier or the child reinitializes it; the same managed mapped-memory exception fails closed. Process preparation reports the filesystem runtime's tracked logical current directory before falling back to native `getcwd` or `PWD`; this keeps descendant execution logical even when libc traversal temporarily entered a prepared physical directory or the caller cleared `PWD`. Replacing the recursion escape hatch safely requires a complete native backend for all overlay host I/O; the hook-only implementation is therefore a cooperative boundary rather than a complete namespace.

For encrypted local files, Broker-recorded completed ranges are merged into a short writeback window and update the affected ciphertext blocks without forcing them to stable storage. Writes through an `O_SYNC` or `O_DSYNC` open, intercepted `fsync`, successful `F_FULLFSYNC`/`F_BARRIERFSYNC`, `MS_SYNC`, mapping teardown or write removal, tracked final close, normal process exit, and the pre-exec path request durable synchronization. A clean durable request skips `sync_all`; after mutations, one durable sync for the shared ciphertext inode satisfies all of its handles. While the runtime remains alive, the parent Broker checks shared plaintext vnodes with registered writable mappings every ten seconds. It compares size, modification time, and change time against a mapping-specific baseline; an unchanged identity performs no body scan, while a changed identity encrypts the vnode-wide union of registered candidate ranges without requesting durable storage. Ordinary writeback updates its independent write baseline and therefore cannot hide a pending mapping change. This periodic path narrows the normal-operation exposure window but does not replace or strengthen native durability boundaries. Final descriptor close sends hook-side fallback ranges with `PrepareClose`, then releases the retained handle after successful native close; the release acknowledgement does not encrypt or synchronize a second time. Other terminal cleanup uses the combined `Close` operation. Normal process exit calls libc `fflush(NULL)` before entering the filesystem guard so buffered writes re-enter managed I/O and preserve the logical offset. When a run ends, the parent controller stops accepting new local Broker connections, drains requests it already accepted, and performs one final flush that first collects each live handle and then durably synchronizes each changed ciphertext inode once. Pre-registered writable mapping ranges and a plaintext identity fallback let it recover changes from a child that exits without closing its descriptors. A host crash or termination of the controller can still lose updates that were never durably synchronized. Opens of one ciphertext inode observe completed mutations through the same plaintext vnode. Ordinary writes on independent opens may overlap; append reservations and preparation operations that can overwrite native writes remain exclusive, and ciphertext publication stays serialized. Writable shared mappings join the same sync and durability boundary. Attribute refresh after synchronization updates the logical path only while it still resolves to the same backing device and inode. An open descriptor whose path was unlinked or replaced can therefore sync and cross exec without failing or modifying the replacement path.

Inherited control-stream acquisition has one 30-second total deadline across its process-local mutex and descendant-shared record lock. A live thread or descendant that stalls while owning either boundary therefore makes a competing transaction return `ETIMEDOUT` instead of waiting forever.

## Executable Preparation

The in-process code-signature inspection cache includes device, inode, size, mtime, ctime (both timestamps at nanosecond resolution), and native file flags. Restoring mtime after an in-place edit does not make the old signature decision reusable. Unchanged identities still avoid repeated signature inspection.

Injectable executables and shebang scripts can run from their original visible paths. When SIP flags, dyld restrictions, library validation, Hardened Runtime, or architecture selection prevent injection, the execution controller copies the selected Mach-O slice into its exact mirrored path below `<workdir>/fs`, applies required processing, and ad-hoc signs it.

For a directly executed binary inside a `.app` containing `Contents/Info.plist`, preparation parses the active 64-bit Mach-O slice before publishing the prepared main image. It resolves `@executable_path`, `@loader_path`, and the image-local plus inherited `@rpath` stack and recursively materializes required bundle-local startup images at their mirrored paths. Absolute dependencies and system shared-cache images remain at their native paths. The traversal rejects malformed load commands, missing required dependencies, dependencies escaping the bundle, more than 512 unique copied images, more than 32 dependency levels, or more than 2 GiB of copied dependency content; missing weak dependencies are ignored and cycles are deduplicated. Each copied loader image is byte-for-byte identical to its source and is atomically published before the main executable is returned. A failed closure may leave reusable non-authoritative loader cache entries but never returns or newly publishes the main executable. If a required image is already `cow` or `whiteout` in the sandbox view, preparation fails rather than replacing that state with lower content. Resources that dyld does not need at startup remain in lower and are reached through the normal logical VFS after Hook initialization; a complete application bundle is never copied.

Prepared executable copies persist across runs. Reuse first requires a matching device/inode/size/timestamp/mode source identity and target OS/architecture variant. The cache record also stores the prepared destination's device/inode/size/timestamp/mode identity: an unchanged destination identity reuses the file without rereading it, while a changed or previously unrecorded identity triggers a complete MD5 comparison with the recorded prepared-output MD5. A matching fallback MD5 refreshes the destination identity and reuses the file; a missing checksum, mismatched MD5, source or target mismatch, unreadable destination, or non-executable destination rebuilds through the existing temporary preparation, architecture selection, ad-hoc signing, and atomic publication flow. This preserves content validation after any observable destination mutation while avoiding a complete read of an unchanged large executable on every exec. Ad-hoc re-signing preserves the source code identifier and ordinary entitlements. Entitlements bound to the source's Apple-private, developer, team, application-group, Keychain-group, rootless, or other vendor signing identity are removed from the prepared copy because an ad-hoc signature cannot validly assert them; the source executable remains unchanged. Capabilities that require a removed entitlement remain unavailable, while unrelated executable behavior can continue with the sanitized copy. The prepared copy still lacks the source Team ID, certificate, designated requirement, TCC grant, and XPC trust relationship, so applications that require one of those identities remain unsupported.

Descendant `posix_spawn` and `execve` calls use the authenticated execution-preparation channel and fail closed when preparation fails. `execvp` PATH search skips existing candidates that are not regular executable files and continues to later components; when `PATH` is absent it uses the macOS `_PATH_DEFPATH` value `/usr/bin:/bin`. If no later candidate succeeds, it returns `EACCES` when at least one candidate was denied and `ENOENT` only when none existed. If native `execve` of the prepared `execvp` candidate returns `ENOEXEC`, the hook prepares `/bin/sh` and invokes it with the prepared candidate followed by the caller's remaining arguments, matching the shell-script fallback expected from `execvp`. Direct execution of an application binary such as `Example.app/Contents/MacOS/Example` is supported; `/usr/bin/open` is rejected with `ENOTSUP`, and NSWorkspace, LaunchServices, or another system-mediated launcher is outside the process-tree and Hook-lifecycle boundary.

The execution store rejects physical paths elsewhere in the private work directory. Paths beneath `<workdir>/fs` are accepted only through overlay state, and covered filesystem APIs lexically normalize physical prepared paths before decoding them into the logical view. This allows a relocated executable to inspect itself and access sibling resources through paths such as `Contents/Resources/../bin/options` without exposing arbitrary work-directory files. Interposed runtime `dlopen` and `dlopen_preflight` calls apply the same decoding, permission, whiteout, upper, and lower rules before passing a stable lower or plain-upper native path to dyld. Path preparation finishes under the filesystem guard, but the guard is released before calling dyld so library initializers and dependency loading continue through normal Hook policy instead of inheriting a recursion bypass. Other private workdir loader paths fail with `EACCES`; encrypted-upper and NFS loader inputs fail with `ENOTSUP` because neither exposes a stable native plaintext path. A custom thread-local `dlerror` message reports preprocessing failures once without replacing later native loader errors. A shebang interpreter goes through the same path, with its optional argument and prepared script path inserted before caller arguments. An executable replaced by encrypted business COW data never falls back to the stale lower executable, but executing that encrypted upper image remains unsupported until the execution protocol can pass an already-decrypted executable descriptor rather than only a path.

## Key Migration

Normal startup never changes an existing key. Migration is explicit and interactive:

```bash
agora-sandbox key migrate --workdir <WORKDIR>
```

The command reads the current and replacement keys as visible text, validates the physical `fs` root as a same-user directory without following its final symbolic link, acquires the same `.fs.lock`, and validates the old key. It discards encrypted `Cached + Copy` write-preparation caches before filename migration so subsequent access falls back to the authoritative lower file, removes inactive Unix-domain socket nodes that cannot remain usable across the migration boundary, then re-encrypts each remaining encrypted business file block by block, leaves logical zero blocks physically sparse, and compares the replacement's plaintext SHA-256 with the plaintext observed from the source before publication. Controller-managed plaintext executable and loader caches and whiteouts are not re-encrypted. A role-validated `.rekey.json` is persisted before replacing any file: destination paths may not alias managed controls, staging and backup names must match their exact internal forms, every entry's paths must share one parent, and paths may not overlap. Recovery resolves every journal operation relative to no-follow directory descriptors, so an intermediate symbolic link cannot redirect removal or restoration outside the encrypted root.

Old ciphertext remains in per-file backups until `.key.json` publishes the new key. Staging, journal/key publication, every replacement or restoration rename, backup cleanup, and journal removal sync the affected parent directories. A failure before the key rename rolls the migration back. If the key rename succeeds but its parent-directory sync cannot be confirmed, the command reports an indeterminate durable-publication error and preserves the journal and backups so the next startup can resolve the visible key state. Once publication is durable, a cleanup failure is reported explicitly as an active-new-key state and cleanup is retried on startup. Startup rolls back an old-key journal or completes cleanup for a committed new-key journal before opening the workspace. Before a later explicit migration begins its normal full-tree scan, it removes only exact `.agora-rekey-<32 hex>.tmp` and `.agora-encrypted-<32 hex>.tmp` staging files left before journal publication; it does not add a recursive scan to ordinary startup and does not infer ownership of or delete an unjournaled backup. Workspace construction and migration have synchronous filesystem/crypto cores; the public async runner and migration APIs dispatch them to Tokio blocking workers. Migration stages return over a channel and the caller's progress callback runs on the async caller rather than the blocking worker. Progress is stage-based rather than byte-based. Identical keys are rejected, and the old key is rejected after a successful migration.

There is no `clean` command or compatibility migration. Persistent state is removed only by explicitly deleting `<workdir>/fs` outside normal sandbox startup while no sandbox holds `.fs.lock`; other configured or temporary work directories are not deleted implicitly.

## Audit And Trace

The callback receives unified network, process, and file events. Process and file events are audit-only; network events may allow, deny, or proxy a connection.

The CLI emits audit events as structured `audit` fields through the project JSON logger. `log.file` selects the unified logger destination and defaults to `<workdir>/runtime/logs/sandbox.log`; a relative value is resolved from the workdir. Missing parent directories are created through normal filesystem path resolution, including symbolic links. The final log file itself is opened without following a symbolic link and must be a same-user regular file. The unified file also receives NFS status and other sandbox lifecycle records, while child stdout and stderr remain inherited without Agora records after logger initialization. A newly created log file uses mode `0600`. Opening an existing file does not change its mode; later permission management remains the caller's responsibility.

The binary-private Runtime Trace viewer is started with:

```bash
agora-sandbox web -c sandbox.json [--no-open]
```

It uses the same configuration loader and compact audit-record schema as `run`, follows the resolved
`log.file`, and invokes the current binary as `agora-sandbox run -c <absolute-config> -e /bin/bash`
inside a pseudoterminal. There is no second tools binary, duplicate Web configuration parser, or
browser-selectable executable. `--no-open` suppresses only automatic browser launch.

Each tail iteration reads at most 1 MiB of appended log data, so a backlog drains incrementally
instead of being allocated as one buffer. The viewer retains at most 5,000 trace events and 8 MiB
of their source log records; it evicts the oldest events when either limit is reached and marks the
snapshot as truncated. Live WebSocket trace batches are bounded by the same per-poll input limit.

PTY input is accepted into a bounded queue of 16 frames, each at most 64 KiB, plus one in-flight frame. A nonblocking native-descriptor worker drains it; input saturation reports a backpressure error rather than blocking the session-control mutex or dropping bytes silently. Stop and resize do not wait for the writer. Output, replay, control, and close messages share a three-second socket-write deadline, so an unresponsive browser cannot retain the controller connection indefinitely. Terminal events carry their session generation and are applied under the hub-state lock; output, errors, and exit notifications from a retired session cannot modify a new session. The running status is published before starting the event bridge, preventing a fast exit from being overwritten by a late running status.

The filesystem hook publishes `filesystem.open` before an intercepted non-allowlisted open and `filesystem.close` before an intercepted tracked close. Operations beneath every effective native-passthrough root, including `/dev`, are deliberately absent from this stream. Events carry the logical path, structured access flags, current process identity, and trace chain. When a prepared executable runs from below `<workdir>/fs`, filesystem, process, and network events translate its process executable identity back to the corresponding logical source path; runtime cache paths and encrypted backing names are never reported as that identity. A successful descendant `posix_spawn` or `exec` carries a bounded, versioned pending command context through a reserved runtime environment field; the new image removes that field and publishes `process.exec.attempt` from its Hook initializer before filesystem initialization, so the event uses the real child PID, PPID, and executable identity. Caller-supplied values for this field are removed or replaced. If preparation or the native process operation fails before a new image starts, the caller publishes the same attempt context with its own identity because no child process exists. Audit protocol version 4 gives every publication a random request ID and uses it as the callback event ID. The first event on a fresh ordinary connection waits only for authentication and request validation; the controller sends that response before invoking the callback. Later events on the same connection use bounded asynchronous socket delivery and do not wait for responses. Each thread reuses its healthy connection and proactively refreshes it after 25 seconds of inactivity, before the controller's 30-second ordinary-connection timeout. A reported write failure removes the cached connection and retries the same encoded request once, but the controller keeps no deduplication cache, so an ambiguous retry may produce repeated callbacks with the same event ID. The one authenticated inherited control stream begins with `ping`, remains available across idle periods and nested sandbox activation, and uses the same one-way event delivery after authentication. If a process-exit filesystem operation occurs after Rust thread-local destruction, the client uses one fresh acknowledged connection or the inherited fallback instead of panicking or dropping the event. Initial authentication, validation, and reported transport failures remain fail-closed. Orderly controller shutdown gives existing audit connections 250 ms in total to drain before aborting them; abnormal termination or a larger backlog can still lose accepted tail events.

## Host Keychain Behavior

The runner does not install a native Keychain-denial policy, and no Keychain API is intercepted or virtualized. Security.framework and `security` clients in descendants use the current user's host Keychain directly. Reads, refreshes, updates, and deletes therefore have the same host-visible effects inside and outside the sandbox.

Filesystem credential locations remain independent COW paths. For example, a CLI may combine configuration below the home directory, files below `~/Library/Application Support`, and a Keychain item. Externally removing one physical upper directory resets only that filesystem subtree and makes the next access fall through to its host lower path; it does not reset other credential directories or Keychain state.

Every run starts with one trace ID. Descendants append an ID and forward a bounded comma-separated chain, following `X-Forwarded-For` style. Process, file, and network events carry the same chain so one command can be correlated with its file and network activity.

## TLS Runtime Files

With TLS interception enabled, the runner reuses or creates the configured CA certificate and key, defaulting to `<workdir>/ca/ca.crt` and `<workdir>/ca/ca.key`. Each generated file is synchronized and atomically published from a same-directory temporary file. Before reusing the automatically managed default pair, the runner validates that the certificate and private key are well formed and match; a partial, malformed, or mismatched default pair is regenerated. A complete explicitly configured pair remains caller-owned and a validation failure is reported rather than overwritten. The per-run temporary directory receives two `0600` client trust artifacts assembled from the sandbox CA and native roots: a PEM bundle for `SSL_CERT_FILE`, `CURL_CA_BUNDLE`, `REQUESTS_CA_BUNDLE`, `PIP_CERT`, `NODE_EXTRA_CA_CERTS`, and `GIT_SSL_CAINFO`, and a JKS v2 store for default Java JSSE clients. The runner and process hook append the JKS properties to `JAVA_TOOL_OPTIONS` while retaining unrelated options and quote the managed store path with JVM option syntax when it contains whitespace; an explicitly configured application trust store remains authoritative. SecTrust clients receive the interception CA through internal hook configuration. The runner does not modify the host Keychain, an installed JDK, or an IDE configuration directory, and there is no public independent trust-anchor option.

Leaf certificates are valid for one day and cached in memory for one hour. DNS names use public-suffix-aware wildcard selection, while IP addresses remain exact. The test suite covers copied `/bin/bash`, system `curl`, transparent CA trust, TLS interception, and a local HTTPS origin without an explicit `--cacert` argument.
